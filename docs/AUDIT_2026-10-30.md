# MedFlow code and experience audit — 30 October 2026

Base reviewed: `master` at `c596b03`. The repository has 236 tracked files and 36 Next.js API route files. This review inspected the active patient, doctor and super admin application, authentication and payment paths, shared navigation and layout, configuration, schema, and existing documentation. Findings below distinguish code evidence from runtime verification.

## Remaining verified risks and limits

- `src/lib/middleware/rateLimiter.ts` stores counters in process memory. Multiple server instances therefore do not share limits, and restarts reset them. Move high-risk limits to a shared store before relying on them as an abuse control.
- `db.json` is tracked and contains seven profile rows and two appointment rows. Confirm these are synthetic data. If any belong to real people, remove the data and assess repository history and downstream copies.
- The repository's `npm run lint` currently scans prototype and history code as well as the active app and reports a large existing error backlog. Establish a clean active-source lint gate, then fix remaining violations in small batches.
- The current security headers in `next.config.ts` do not include a Content Security Policy. Plan and test a policy for Firebase, Razorpay, and the video provider; do not deploy an untested policy that blocks care flows.
- The existing roadmap documents include descriptions of routes that no longer exist. Update them after each release so operational decisions use the current application.

## Verification

- Production build: completed with Next.js 16.4.3, including TypeScript and generated pages (`.next/BUILD_ID` and prerender manifest produced).
- Lint on changed TypeScript files and the patient API directory: passed. Full `npm run lint`: failed with 635 findings, mostly in existing prototype and app code. The new menu issue it identified was corrected and the changed-file check rerun.
- Dependency audit after compatible fixes: `npm audit --omit=dev` reports 13 production advisories (9 moderate, 4 high, 0 critical). This is an advisory count, not a finding that each vulnerable path is exploitable here.
- Public landing page: HTTP 200 at 375px, 768px and 1280px. At each width, document width matched viewport width. Key sections appeared when scrolled into view. The unconfigured local production server returned an error from `/api/doctors`, so this check displayed fallback specialties and did not exercise live doctor data or authenticated pages.

Authenticated booking, payments, video visits, notifications, and visual checks of all three portals require configured Firebase, Supabase, Razorpay, and video test accounts. No live patient data or production transactions were used. Code changes here do not establish healthcare regulatory compliance.
